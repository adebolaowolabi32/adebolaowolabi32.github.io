SourceDesk

Try demo ↗Source code ↗

An early SourceDesk answer implied it knew what had happened to someone’s payment. It only had documentation. That mistake shaped how the app handles account questions and how I reviewed the generated answers.

Answering from the guides

SourceDesk searches 12 fictional payment guides. The default mode returns matching passages directly. With GPT and pgvector enabled, it writes an answer using retrieved passages and includes quotes you can check. Questions about a specific account go to review, as do questions the guides cannot answer.

Keeping citations tied to the answer

Each search index records which documents and embedding model it was built from. A new index becomes active only after indexing finishes. Saved answers also keep a copy of their source passages, so editing a guide does not change the evidence attached to an old answer.

For this small set of guides, I used exact vector search. The app checks that each quoted passage exists in the retrieved source. That catches invented quotations. It cannot tell whether the model has interpreted a real passage correctly, which still needs review.

What the first tests caught

The first run passed 38 of 40 questions. It missed a paraphrased role name and answered a question about someone’s account with general documentation. I fixed the normalization and scope checks, then reran the same suite: 40 of 40 passed.

A separate live test caught the account-specific wording mentioned above. I changed the prompt to describe what the documentation says conditionally, rather than imply knowledge of a particular payment.

Try an account question

In the demo, ask a documentation question, inspect its quoted source, then ask about your own missing funds. Compare the answer and handoff paths. The hosted preview uses prepared synthetic responses; it does not call a paid model.

Reading the test results

  • All 40 development questions pass after fixes. I saw the full set during development, including the subset originally called “holdout,” so these results cannot measure performance on unseen questions.
  • The live test indexed 30 passages and passed five smoke cases. It confirms that the API and retrieval path work together. Five cases are too few to judge general answer quality.
  • Reviewing the answers caught a wording problem that the automated checks missed. Claim support has not been independently graded.

What still needs testing

The app has only been tested with this small collection of guides. The next useful evaluation would use questions written independently of the implementation, with people checking whether each answer follows from its sources and whether a handoff was needed. That work is still outstanding.
